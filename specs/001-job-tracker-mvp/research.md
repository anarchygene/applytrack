# Research: ApplyTrack MVP

All Technical Context unknowns are resolved below. Versions were checked against the npm registry
on 2026-11-05.

## R1. Runtime and language

- **Decision**: Node.js 24 LTS (engines `>=22.12`), TypeScript **6.0.x** in strict mode, ES modules.
- **Rationale**: Node 24 is the current LTS and is what the author has installed. TypeScript 7
  (the native Go compiler) is out, but `typescript-eslint` still declares `typescript <6.1.0`, so
  6.0 is the newest version the lint toolchain supports.
- **Alternatives**: TS 7 + no type-aware linting (rejected: loses lint coverage); Bun/Deno
  (rejected: less common in job listings, weaker Render/Neon docs).

## R2. HTTP framework and contract

- **Decision**: Fastify 5 + `fastify-type-provider-zod` 7 + Zod 4; `@fastify/swagger` generates
  OpenAPI 3.1 from the route schemas; Scalar (`@scalar/fastify-api-reference`) serves interactive
  docs at `/docs`.
- **Rationale**: Satisfies Constitution I — one Zod schema per route gives runtime validation,
  static types and docs. Fastify's `inject()` enables fast HTTP-level tests without opening ports.
- **Alternatives**: NestJS (more boilerplate, decorators hide flow); Express (no built-in schema
  pipeline); Swagger UI (works, but Scalar is a more polished reviewer experience).

## R3. Data access and migrations

- **Decision**: PostgreSQL 17 via `pg` (node-postgres) + Drizzle ORM 0.45; SQL migrations
  generated by drizzle-kit, committed under `apps/api/drizzle/`, applied by a `migrate` script at
  deploy time (Render pre-deploy command) and in test setup.
- **Rationale**: Drizzle is typed, SQL-shaped and has no runtime query engine; aggregate statistics
  can be written as real SQL with `sql` templates. `pg` is the most widely used driver and works
  with Neon's pooled endpoint.
- **Alternatives**: Prisma (heavier, separate engine, awkward for aggregate SQL); Kysely (good, but
  no migration generator).

## R4. Authentication and sessions

- **Decision**: Server-side sessions with opaque random tokens (32 bytes, base64url). Only the
  SHA-256 hash of the token is stored in `sessions`. The token is delivered as an `httpOnly`,
  `Secure` (in production), `SameSite=Lax` cookie, and is also returned in the login/register
  response body so non-browser clients can send `Authorization: Bearer <token>`. Sliding expiry
  of 7 days, extended at most once per hour per session to avoid write amplification. Passwords
  are hashed with argon2id via `@node-rs/argon2` (prebuilt binaries, no node-gyp on Windows).
- **Rationale**: Spec FR-003 requires sign-out to invalidate a session immediately, which stateless
  JWTs cannot do without a denylist. Hashing tokens means a database leak does not leak live
  sessions. Constitution III requires argon2id.
- **CSRF**: The SPA is served from the same origin as the API (see R7), cookies are `SameSite=Lax`,
  and every mutating endpoint requires `Content-Type: application/json` (or has no body and uses a
  non-simple method like DELETE/PATCH), which browsers cannot send cross-site without a CORS
  preflight that the API does not grant. No CSRF token is required.
- **Alternatives**: JWT access + refresh tokens (more moving parts, revocation complexity);
  third-party auth (Clerk/Auth0 — hides the backend work this project is meant to show).

## R5. Rate limiting

- **Decision**: `@fastify/rate-limit` with the in-memory store: 10/min per IP on `/v1/auth/*`,
  5/hour per IP on demo creation, 300/min per user globally. The AI daily limit (FR-052) is enforced
  in the database: count of the user's tailorings in the last rolling 24 hours, so it survives
  restarts and is exact.
- **Rationale**: A single API instance (Constitution IV) makes an in-memory store correct; Redis
  would be unjustified infrastructure.
- **Alternatives**: Redis store (needed only when horizontally scaled).

## R6. AI provider

- **Decision**: Anthropic Claude via `@anthropic-ai/sdk`, behind a `TailoringProvider` interface with
  two implementations: `ClaudeTailoringProvider` and `FakeTailoringProvider` (tests). Enabled only
  when `ANTHROPIC_API_KEY` is set; model configurable with `ANTHROPIC_MODEL` (default
  `claude-opus-5-5`; operators can choose `claude-haiku-5-5` to cut cost). Structured output uses
  `client.beta.messages.parse` with `betaZodOutputFormat`, so the response is validated against the
  same Zod schema; the output is then normalised (trimmed, length-capped, de-duplicated). On models
  that support it, the server-side refusal fallback (`fallbacks: "default"`) is enabled. Effort is
  set explicitly to `medium`. Timeout 60 s with the SDK's 2 retries; resume and job description are
  each capped at 20,000 characters; the prompt treats both as untrusted text.
- **Rationale**: Constitution VI. Forced tool calls are rejected by current Claude models, and
  structured outputs give schema-valid JSON directly.
- **Errors**: Not configured → `503 ai_unavailable`. Provider error/timeout/refusal →
  `502 ai_provider_error` (not counted against the limit). Limit hit → `429 ai_daily_limit` with
  `Retry-After`.

## R7. Frontend and deployment shape

- **Decision**: Vite + React 19 + TypeScript + React Router + TanStack Query + Tailwind CSS 4.
  The API client is generated from the committed OpenAPI document with `openapi-typescript` and
  called through `openapi-fetch`, so the frontend is type-checked against the real contract.
  In production the API serves the built SPA via `@fastify/static` from the same Docker image and
  origin.
- **Rationale**: One Render web service + one Neon database keeps hosting free and avoids
  cross-site cookie problems (`onrender.com` is on the public suffix list, so a separate static site
  would be a different site and its cookies would be third-party). Generated client types
  demonstrate contract-first development end-to-end. The constitution's "API + static site" is
  satisfied by one service that serves both.
- **Alternatives**: Separate Render static site + CORS + bearer tokens in `localStorage` (rejected:
  XSS-exposed tokens, CORS complexity); Next.js (blurs the backend focus).

## R8. Testing strategy

- **Decision**: Vitest 5. Unit tests for pure domain modules (stage transitions, reminder grouping,
  stats maths). Integration tests build the real Fastify app and call it through `app.inject()`
  against a real PostgreSQL test database; each test file truncates all tables in `beforeEach`.
  Integration files run sequentially (`fileParallelism: false`) to share one database safely.
  Locally the database comes from `docker compose`; in GitHub Actions from a `postgres:17` service
  container. The AI provider is always the fake in tests.
- **Rationale**: Constitution II (real DB, no third-party network calls).
- **Alternatives**: Testcontainers (nice, but slower on Windows and needs Docker in every run);
  pg-mem (not real Postgres — rejected by the constitution).

## R9. Observability and operations

- **Decision**: Fastify's built-in pino logger (JSON in production, `pino-pretty` in dev) with
  `genReqId` using incoming `x-request-id` or a UUID; redact `authorization`, `cookie`, `password`,
  `resumeText`. `GET /health` returns `{status:"ok"}`; `GET /ready` runs `SELECT 1`. Config is
  parsed by a Zod schema at startup. `SIGTERM`/`SIGINT` → `app.close()` which closes the pool.
  `@fastify/helmet` sets security headers.
- **Rationale**: Constitution V.

## R10. Demo accounts (FR-064)

- **Decision**: `POST /v1/auth/demo` creates a user with `is_demo = true`, a random unguessable
  email (`demo-<uuid>@demo.applytrack.local`), seeds ~15 applications with realistic history,
  reminders and a sample resume, and signs the visitor in. An in-process interval (every 15 min,
  plus once at startup) deletes demo users older than 24 hours; cascading foreign keys remove their
  data. Demo users cannot use the AI feature unless `AI_ALLOW_DEMO=true` (protects the operator's
  API budget).
- **Rationale**: Each reviewer gets a private sandbox; nobody can vandalise a shared demo login.

## R11. Repository layout and tooling

- **Decision**: npm workspaces monorepo (`apps/api`, `apps/web`); ESLint 10 flat config with
  `typescript-eslint`; Prettier; GitHub Actions workflow running lint, typecheck, API tests against
  Postgres, OpenAPI drift check, and web build. Multi-stage Dockerfile at the repo root.
- **Rationale**: Constitution "Development Workflow and Quality Gates".
